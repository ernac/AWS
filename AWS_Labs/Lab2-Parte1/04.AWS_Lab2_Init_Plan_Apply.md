# TERRAFORM INIT, PLAN, APPLY


>The **`init` $\rightarrow$ `plan` $\rightarrow$ `apply`** cycle is the core workflow in Terraform for transforming declarative code (HCL) into real cloud infrastructure.

# 1.TERRAFORM INIT

>Required before running any other command in the working directory.

Prepares the local working directory. During this step, Terraform does not modify any cloud resources; instead, it sets up all necessary dependencies:

- **Backend Initialization:** Configures where the state file (`terraform.tfstate`) will be stored (locally or in remote backends such as Amazon S3 with DynamoDB state locking, Azure Blob Storage, or Terraform Cloud).
    
- **Provider Downloads:** Reads the `required_providers` blocks, downloads the necessary plugin binaries (e.g., AWS, Azure, Google Cloud) into the hidden `.terraform/` folder, and writes or validates their cryptographic hashes in `.terraform.lock.hcl`.
    
- **Module Installation:** Downloads the code for reusable modules declared in the configuration (from the Terraform Registry, Git repositories, or local file paths).

# 2.TERRAFORM PLAN

>Safe read-only execution check - causes no side effects on infrastructure.

Generates an execution plan by comparing three sources of truth: the **HCL configuration code**, the **current state file**, and the **real-world cloud infrastructure**.

- **State Refresh:** Performs read-only API calls to the target providers to synchronize the local state with the actual infrastructure in the cloud, detecting configuration drift.
    
- **Delta Calculation:** Determines the exact set of actions required to bring real-world infrastructure into alignment with the declarative HCL code.
    
- **Plan Output:** Displays proposed actions in the terminal using standard status symbols:
    
    - `+ create`: The resource will be created from scratch.
        
    - `~ update in-place`: Specific attributes will be modified without destroying the resource.
        
    - `- destroy`: The resource will be deleted.
        
    - `-/+ replace`: The resource will be destroyed and recreated (typically caused by modifying an immutable attribute).
        
- **Plan File Export (Optional):** Allows saving the compiled execution plan to a file (`-out=tfplan`) to ensure the subsequent apply step executes that exact projection without drift.
    

# 3.TERRAFORM APPLY

>Execution phase that directly alters cloud infrastructure.

Applies the planned changes to the cloud environment and updates the state file.

- **Interactive Confirmation:** Unless a pre-compiled plan file (`tfplan`) is provided, Terraform runs a plan internally and requires explicit user confirmation (`yes`) before making any changes.
    
- **API Execution and Concurrency:** Terraform builds a dependency graph and issues the necessary API calls in parallel (defaulting to 10 concurrent operations), strictly respecting both implicit and explicit dependencies (`depends_on`).
    
- **State Persistence:** As resources are provisioned, updated, or destroyed, the `.tfstate` file is updated to record the new resource IDs, metadata, and attributes returned by cloud APIs.
    

# WORKFLOW COMPARISON SUMMARY

|**Command**|**Primary Purpose**|**Modifies Cloud Infrastructure?**|**Modifies .tfstate?**|
|---|---|---|---|
|**`terraform init`**|Download providers/modules and configure the backend|No|No|
|**`terraform plan`**|Preview changes and detect infrastructure drift|No|No (in-memory only)|
|**`terraform apply`**|Provision, update, or destroy infrastructure|**Yes**|**Yes**|
