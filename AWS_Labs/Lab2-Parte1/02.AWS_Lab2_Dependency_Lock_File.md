
# DEPENDENCY LOCK FILE

A **dependency lock file** in Terraform—specifically the file named `.terraform.lock.hcl`—is an automatically generated file that acts as a **receipt and contract** for the exact versions of external providers (plugins) used in your project.

## THE REAL-WORLD ANALOGY: A RECIPE VS. EXACT INGREDIENTS

Imagine cooking a dish using a recipe that says: _"Add olive oil and shredded cheese."_

- On Monday, you buy mild cheddar. The dish tastes great.
- On Friday, your colleague cooks the same recipe, but buys extra-sharp aged cheese. The dish tastes completely different or might even be ruined.

In Terraform:

- Your **configuration code** (`main.tf` or `versions.tf`) is the general recipe. You might specify: `version = "~> 5.0"` (meaning "any version in the 5.x range").
    
- The **lock file** (`.terraform.lock.hcl`) is the shopping receipt that says: _"We used exactly AWS Provider version `5.31.0` with checksum `xyz`."_ Every team member and CI/CD pipeline who reads that receipt uses the exact same ingredient.
    
## WHAT DOES IT ACTUALLY DO?

1. **Pins Exact Provider Versions:**
    
    Even if your code uses flexible version constraints (like `>= 4.0`), once you run `terraform init`, Terraform records the single exact version that was downloaded. Subsequent runs of `terraform init` will strictly install that recorded version, preventing accidental breaking changes when a provider author publishes a newer version.
    
2. **Ensures Cryptographic Integrity (Security):**
    
    The lock file records cryptographic **hashes** (checksums) for the provider packages across supported operating systems and architectures. If a provider's source binary is altered or tampered with maliciously on the registry, Terraform detects the hash mismatch and refuses to run.
    
3. **Guarantees Consistency Across Teams and CI/CD:**
    
    Because the file guarantees that your local laptop, your teammate's computer, and your deployment server use identical provider binaries, it eliminates the classic _"it worked on my machine"_ problem.
    

## WHAT DOES IT LOOK LIKE INSIDE?

A typical `.terraform.lock.hcl` entry looks like this:

Terraform

```
# This file is maintained automatically by "terraform init".
# Manual edits may be lost in future updates.

provider "registry.terraform.io/hashicorp/aws" {
  version     = "5.31.0"
  constraints = "~> 5.0"
  hashes = [
    "h1:K8y...exampleHash...",
    "zh:4d2...exampleHash...",
  ]
}
```

## KEY OPERATIONAL RULES

- **Commit it to Version Control:** Always commit `.terraform.lock.hcl` to Git alongside your `.tf` files. (Do **not** commit the `.terraform/` hidden folder, which contains the downloaded binaries).
    
- **Does It Lock Modules?** No. The lock file currently applies **only to Terraform providers** (plugins like AWS, Azure, Google, Kubernetes), not to reusable Terraform modules.
    
- **How to Upgrade:** Terraform will not automatically fetch newer versions within your constraint as long as the lock file exists. To deliberately upgrade, you must run:
    
    Bash
    
    ```
    terraform init -upgrade
    ```
    
    This instructs Terraform to check for newer compatible versions, download them, and rewrite the lock file.
